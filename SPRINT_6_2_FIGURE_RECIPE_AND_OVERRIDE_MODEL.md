# Sprint 6.2: Figure Recipe And Override Model

## Status

Parked draft for review. Do not implement until Sprint 6.1 has identified the current figure flow and integration points.

## Purpose

Add or adapt structured data models for figure recipes, reviewer style overrides, figure versions, and render jobs.

These records must make figure styling reproducible and auditable without mutating source data, source geometry, or analysis outputs.

## Required Concepts

### Figure Recipe

Represents the deterministic render intent for a figure:

- figure ID
- project ID
- matrix target / section target
- source layer references
- comparison-unit layer references
- default layer order
- default labels/display names
- default styles
- extent policy / planned render extent
- legend inputs
- basemap references
- generated artifact references

The recipe should be derived from existing generated figure metadata where practical.

### Analysis Snapshot

Represents the frozen analytical truth used by figure rendering.

The first implementation may reference existing canonical artifacts rather than copy large data:

- source status
- project area
- comparison units
- comparison-unit constraints
- deliverable figure artifact
- figure extent plan
- layer paths

The snapshot must make clear that style regeneration is tied to a known analysis/source state.

### Figure Style Override

Sparse reviewer presentation metadata:

```text
FigureStyleOverride
  id
  figureId
  projectId
  analysisSnapshotId
  createdBy
  createdAt
  updatedAt
  overrides
    - layerId
    - visible
    - zIndex
    - displayName
    - fillColor
    - fillOpacity
    - strokeColor
    - strokeWidth
    - pointSize
    - labelVisible
    - labelField
```

Persist only changed values. Defaults remain in the recipe/base renderer.

### Figure Version

Tracks render outputs:

- figure ID
- version number
- created timestamp
- generated by system or reviewer
- style override reference
- render job reference
- output artifact path/reference
- approval state

### Render Job

Tracks regeneration execution:

- job ID
- project ID
- figure ID
- analysis snapshot ID
- figure recipe ID
- style override ID
- output format
- status
- errors/warnings
- started/completed timestamps

## Data Model Requirements

- Model records are JSON-serializable and project-local.
- Override records are sparse and independently auditable.
- Default styles are not duplicated into every override unless changed.
- Reset-to-default removes or clears the override, not the recipe.
- Version records preserve previous outputs.
- Approved outputs are never silently overwritten.
- Source records, source files, analysis artifacts, and generated metrics are not mutated.

## Suggested Artifact Placement

Final paths should be chosen after Sprint 6.1, but initial candidates are:

- `projects/<project_id>/maps/figure_recipes/figure_recipes.json`
- `projects/<project_id>/maps/figure_style_overrides/figure_style_overrides.json`
- `projects/<project_id>/maps/figure_versions/figure_versions.json`
- `projects/<project_id>/maps/figure_render_jobs/figure_render_jobs.json`
- regenerated image versions under `projects/<project_id>/maps/figures/versions/`

If existing conventions point elsewhere, prefer the existing convention.

## Migration / Default Handling

Existing autogenerated figures should become implicit version `v1` records without requiring an immediate regeneration.

Existing review queue figure items should continue to work if no style override or version record exists.

## Tests

Add focused tests for:

- default recipe creation from an existing figure artifact
- sparse override serialization
- reset-to-default clearing only override metadata
- version record creation for autogenerated v1
- render job record validation
- no mutation of source/analysis artifact paths during model creation

## Definition Of Done

- Data structures exist for recipes, overrides, versions, and render jobs.
- Existing autogenerated figures can be represented without breaking current review/export flows.
- Sparse override behavior is covered by tests.
- Model docs explain that styling is presentation metadata only.
