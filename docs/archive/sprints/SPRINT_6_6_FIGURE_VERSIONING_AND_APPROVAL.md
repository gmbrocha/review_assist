# Sprint 6.6: Figure Versioning And Approval

## Status

Parked draft for review. Do not implement until regeneration creates versioned outputs.

## Purpose

Implement figure version history and approval state tied to exact figure versions.

## Figure Version Metadata

Each version should track:

- figure ID
- project ID
- version number
- created timestamp
- generated by system or reviewer
- analysis snapshot reference
- figure recipe reference
- style override reference
- render job reference
- output artifact path/reference
- approval state
- superseded/current flags if needed

## Version States

Suggested states:

- autogenerated
- modified
- regenerated
- approved

The state model should remain explicit and compact. Do not overload standard review queue status unless that is the cleanest existing integration after Sprint 6.1.

## Approval Requirements

- Approval targets one exact figure version.
- Approved version becomes the export/report target.
- Previous versions remain accessible.
- Later edits create new versions rather than altering the approved version.
- Approved outputs are not silently overwritten.
- Approval records should include timestamp and actor metadata when available.

## Version History Example

```text
Figure 4
v1 autogenerated
v2 reviewer hid duplicate hydro layer
v3 reviewer adjusted wetland opacity
approved version: v3
```

## UI Requirements

Expose enough version history for review:

- current version
- approved version, if any
- latest regenerated version
- previous versions list
- version artifact links
- approval action for selected version

Side-by-side comparison is deferred.

## Tests

Add focused tests for:

- autogenerated v1 is represented
- each regeneration increments version number
- previous versions remain in history
- approving a version records exact version identity
- later regeneration does not alter approved version
- approved version resolver returns approved version first
- version history survives reset-to-default style action

## Definition Of Done

- Every figure can have an auditable version history.
- Approval is tied to an exact version.
- Prior versions remain accessible.
- Later edits create new versions and do not silently overwrite approved outputs.
