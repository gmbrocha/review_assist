# OVERALL_CONTEXT.md

# Overall Project Context

This document captures the high-level operational, product, and domain context for the Alternatives Review Workflow project.

This file exists to reduce project drift and preserve the original intent, philosophy, and workflow assumptions across future development sessions.

---

# Core Product Concept

The project is an alternatives review assistant for environmental/contextual planning workflows.

The system helps generate structured, source-backed, pre-review findings packages for human professionals reviewing multiple proposed project alternatives.

The tool does not make recommendations or automatically select a preferred alternative.

The current product goal is "no blank page." The system should attempt to generate a comprehensive first-pass package that a reviewer can inspect, correct, remove from, add to, edit, and finalize.

The tool assists with:
- contextual GIS review
- repeatable spatial checks
- findings organization
- report drafting
- map and figure drafting
- comparison table drafting
- appendix/reference package assembly
- review workflow acceleration
- uncertainty preservation
- source traceability

The human reviewer remains responsible for:
- interpretation
- edits
- verification
- acceptance/rejection
- final reporting
- professional judgment

---

# Stable Workflow Pattern

The stable workflow pattern is:

1. User provides:
   - project footprint
   - study area
   - proposed alternatives
   - optional GIS layers/maps/context files

2. System:
   - normalizes geometries
   - crops/intersects relevant source layers
   - performs repeatable contextual checks
   - generates findings
   - drafts structured report language
   - drafts map figures and comparison tables
   - compiles reference appendices when available
   - produces a pre-review findings package

3. Human reviewer:
   - validates findings
   - removes false positives
   - adds missing context
   - edits report language
   - finalizes deliverables

---

# Product Boundary

The system is NOT:
- a recommendation engine
- an autonomous environmental reviewer
- a regulatory authority
- a final environmental determination system
- a hard-scoring/ranking system

The system SHOULD:
- assist review
- reduce blank-page work
- reduce repetitive GIS compilation work
- improve consistency
- attempt comprehensive first-pass coverage
- preserve uncertainty
- support professional workflows

---

# Human-In-The-Loop Philosophy

This project follows a strict human-in-the-loop philosophy.

The system creates reviewable artifacts, not invisible decisions.

Examples:
- GIS intersections create draft findings.
- Imagery observations create review items.
- AI-generated language creates editable draft text.
- Human reviewers remain authoritative.

Nothing generated by the system should be treated as final truth without human review.

---

# Screening-Level Analysis Philosophy

The system is intended primarily for desktop screening-level review and report drafting.

Public GIS datasets from government agencies, educational institutions, and authoritative public infrastructure sources should generally be treated as reliable baseline datasets for screening. That does not make the outputs field verified.

Outputs may help identify:
- potential constraints
- possible crossings
- adjacency concerns
- permitting implications
- resource conflicts
- areas requiring additional review

Outputs should not be treated as field-verified truth unless independently confirmed.

The system should preserve:
- uncertainty
- missing data
- source age
- review requirements
- reviewer judgment

Configurable corridor and buffer widths are expected. Early trail assumptions may fall in the 50 to 100 foot range, but this must remain project-configurable and should not be embedded as a fixed product rule.

# Evidence Types

The system may eventually work with multiple classes of evidence.

These must remain distinguishable.

## 1. Authoritative GIS Datasets

Examples:
- wetlands
- hydrography
- FEMA
- soils
- parcels
- critical habitat
- cultural resources

These are source-backed and citable.

## 2. Derived Spatial Measurements

Examples:
- overlap length
- acreage in buffer
- crossing counts
- nearest distance
- adjacency calculations

These are generated from analysis logic.

## 3. Imagery-Observed Features

Examples:
- possible pond
- recent clearing
- informal access road
- visible disturbance
- possible structure

These are observational and should require review.

They are NOT authoritative facts.

## 4. Human Reviewer Annotations

Examples:
- reviewer notes
- accepted findings
- rejected findings
- field verification notes
- interpretation adjustments

Human annotations are authoritative workflow actions.

## 5. AI-Assisted Narrative Synthesis

Examples:
- draft report paragraphs
- summaries
- findings descriptions
- comparison language

AI-generated language should always remain editable and reviewable.

# Spatial Context Philosophy

The project is primarily interested in resources that:
- intersect
- touch
- cross
- overlap
- fall within meaningful adjacency distance

Examples:
- wetland crossings
- wetland adjacency
- stream/river crossings
- floodplain overlap
- disturbed corridor overlap
- pristine area overlap
- utility conflicts
- bridge implications

Not all nearby features are automatically relevant.

The workflow should avoid over-reporting noise.

# Imagery and Visual Review Philosophy

Aerial imagery may reveal features not present in authoritative GIS layers.

Examples:
- ponds
- new clearing
- newer roads
- newer infrastructure
- disturbed areas

Imagery observations should:
- remain review items
- preserve uncertainty
- avoid overclaiming
- support reviewer awareness
- include imagery source/date when known
- be separated from deterministic source-backed findings

Example phrasing:

"Recent aerial imagery appears to show a pond near the proposed corridor. This feature was not identified in the reviewed wetland dataset and should be verified by the project team."

# Report Philosophy

Generated reports are:
- pre-review drafts
- editable
- source-backed where possible
- descriptive
- review-oriented
- comprehensive first-pass packages where feasible

Reports should avoid:
- final recommendations
- autonomous conclusions
- fake precision
- unsupported certainty

Reports may include:
- findings tables
- alternative comparison matrices
- narrative summaries
- map references
- static report figures
- appendices/reference material
- uncertainty notes
- review requirements
- source references

The system should eventually support a compilation/export workflow that gathers findings, tables, maps, draft narrative, provenance notes, and appendices into one editable draft package.

---

# LLM-Assisted Synthesis Philosophy

GPT or other LLM-assisted steps may be useful for:
- draft narrative generation
- findings summarization
- implication phrasing
- uncertainty wording
- report synthesis
- pre-review sanity checks
- structured finding normalization

These steps must not replace deterministic GIS/source analysis.

LLM outputs should:
- be grounded in structured findings
- preserve uncertainty
- avoid unsupported conclusions
- remain editable and reviewable
- never select or recommend a preferred alternative unless the project scope is explicitly changed and documented

---

# Preferred Comparison Style

Avoid hard scoring/ranking systems.

Prefer:
- descriptive findings
- qualitative classifications
- contextual summaries
- comparative matrices

Examples:
- low/moderate/high concern
- direct crossing
- adjacent
- requires review
- unknown
- no mapped conflict identified

The system should support human interpretation rather than replacing it.

# Anti-Drift Notes

The project should resist:
- premature complexity
- recommendation logic
- hidden decision-making
- excessive automation
- unverifiable AI claims
- black-box outputs

The intended direction is:
- deterministic infrastructure first
- AI synthesis second
- human review mandatory
- provenance preserved
- uncertainty surfaced clearly
